## 严重程度图标参考

在整个报告中保持一致使用：

| 严重程度 | 图标 | 适用情况 |
|---|---|---|
| 严重 | 🔴 | RCE、认证绕过、明文凭证存储 |
| 高危 | 🟠 | SQL 注入、SSRF、路径穿越、访问控制失效 |
| 中危 | 🟡 | IDOR、弱加密算法、缺少频率限制、信息泄漏 |
| 低危 | 🔵 | 次要加固缺口、缺少响应头、冗余错误信息 |
| 信息 | ℹ️ | 风格问题、影响极低的观察 |

## 报告质量要求

- 每个发现**必须**包含全部七个部分：标题、严重程度、代码片段、调用链、根因、PoC、修复建议。
- 代码片段必须以注释形式包含精确的文件路径和行号。
- 调用链必须从 HTTP/gRPC/CLI 入口点一路追踪到漏洞操作——不能止步于处理函数。
- PoC 必须具体——模糊的"攻击者可能……"描述（无利用载荷）不可接受。
- 根因必须解释漏洞的*机制*，而非仅描述代码做了什么。
- 修复建议必须包含可运行的 Go 代码，而非只是文字建议。
